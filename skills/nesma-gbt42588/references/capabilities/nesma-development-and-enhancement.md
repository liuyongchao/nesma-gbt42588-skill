# 识别变更并计算开发、增强、重建规模

## R — 原文

> “EFP = ADD + DEL + CHGA”
> “新应用程序的功能规模等于它要替换的旧应用程序的功能规模。”

出处：GB/T 42588—2023，5.6.4公式(4)、5.5.4，印刷16、14页／PDF20、18页；变更定义见5.7，印刷16–17／PDF20–21。

## I — 自述

应用规模是某个时点的功能存量，项目规模是本项目涉及的功能范围。
删除会减小应用，却仍是增强项目的一部分。
修改功能按修改后的完整功能计入项目，而不是只计新旧差额。
计算增强后的存量，则必须扣掉修改前功能再加入修改后功能。
字段变化不必跨越复杂度等级，功能修改也可能发生。
被变更事务使用的既有数据不自动成为已修改数据功能。
一次性转换只计入相应项目，不混进长期运行应用的存量。
完全重建可以功能净增为零，但必须重建的项目并非零规模。
跨应用或子项目必须先固定各自边界，再解释合计与整体的区别。

## A1 — 原文算例

说明性例题：5.6.1表2，印刷14／PDF18。初始应用1000FP。版本1新增200、删除40、修改前80、修改后100：增强项目`200+40+100=340FP`，应用`1000+200−40+100−80=1180FP`。版本2以1180为基线，新增500、删除100、修改前220、修改后200：项目800FP，应用1560FP。表未另列转换功能，不自行补入转换量。

## A2 — 何时使用

- “这次增删改是多少功能点，上线后总量多少／enhancement project versus application size”。
- “字段长度/类型改了算修改吗／DET change and impact analysis”。
- “新建、迁移转换、整体重写该怎么算／development, conversion, redevelopment sizing”。

与相邻能力的区分：先用 `nesma-scope-and-method` 确定对象；每个功能的类型与分值由识别和复杂度能力完成。本能力决定变更归属与跨版本公式，不从代码行数推功能修改，也不代替 `nesma-growth-classification` 判断需求细化来源。

## E — 执行

**输入契约。** 必须有应用/子项目边界、项目类型、需求变更前后版本、功能ID对应关系、增/删/改/不变证据、各功能前后FP及必要转换清单。所有汇总为非负整数FP。增强后应用需AFPB与CHGB；增强项目核心值只需ADD、DEL、CHGA。缺某项用未知状态，不能填0。已知0须有“无该类变更”的依据。

1. **确定路径及范围。** 新应用开发走开发路径；增强走增删改路径；必须构建整个替代应用的再工程走开发项目路径（5.6.5）。同功能替换的应用存量等于旧应用；替换同时增强时，按5.5.4记录选用的新应用或既有应用增强计数路径。普通局部技术重构不自动等于整体重建。每个子系统是否独立存在、独立运行、由独立项目实现要有事实；NR06边界不清时暂停共享项确定汇总。
2. **对照5.7建立变更表。** 先确认用户功能规格确实改变，再检查直接和连带影响。每个功能只能在本次版本中归入一个主要变更集合；若主要目的改变，应重新识别功能身份并明确新增/删除关系，不能硬套“同一事务修改”。
   - 事务修改：主要目的不变且任一成立——其DET增/删/改；所用逻辑文件增/删；变更的数据功能中至少一个修改DET确属该事务的一部分；验证、计算等逻辑处理改变。需记录受影响DET/文件/逻辑证据，不把所有读取同一文件的事务自动列为修改。
   - 数据修改：DET增/删/改导致结构变化，或数据功能性质发生ILF↔ELF变化。仅被新增/变更事务引用，不足以认定该数据功能修改。
   - DET修改：长度、数据类型或小数位数变化。变化须是用户功能规格变化；纯实现存储调整不能凭名称自动计。即使前后FP相同，已成立的功能修改仍纳入CHGA。
3. **给各集合独立计数。** ADD为新增后的完整功能FP；DEL为被删除的原功能FP；CHGB/CHGA必须是同一组已修改功能的前/后分值。按开发功能相同规则识别及赋值，不只计字段差额。既有未改ILF/ELF不作为增强项目变更项，但仍可参与相关事务FTR。
4. **按路径计算，保持整数。**

| 输出 | 公式 | 必要条件 |
|---|---|---|
| 增强后应用AFPA | AFPB + ADD − DEL + CHGA − CHGB | 同一应用基线及全部五量 |
| 增强项目核心EFP | ADD + DEL + CHGA | 确认增删改集合 |
| 含必要转换的增强项目 | EFP + conversion | 转换是本次变更必须制作的软件功能 |
| 开发项目 | new_application + conversion + other_application_changes | 明确各集合边界、无重叠；其他应用是改动量，不是其完整存量 |
| 同功能整体重建项目 | 新构建应用规模 + 必要转换 + 本项目其他应用变更 | 应用存量与项目交付范围分开 |

一次性转换从应用存量排除。多个应用分别计算新存量，不能从一个“其他应用改动量”推回这些应用总规模。并行独立子项目合计可以高于整应用规模；同一整体应用内共享LF仍须去重。
5. **检查基线与缺口。** 删除和修改前集合应属于有效基线，彼此不重叠；结果不应为负。缺CHGB时可在其他条件充分时给增强项目值，但不给确定AFPA。任何未识别或争议功能保留为待计项，不能从小计推完整总量。
6. **复算并报告。** `resources/nesma_calc.py` 的enhancement请求含add、deleted、changed_after、conversion，及计算存量所需baseline、changed_before；输出project_core_fp、project_fp，基线两项齐才输出application_fp。development请求含new_application、conversion、other_application_changes。命令 `python nesma_calc.py input.json --output result.json`；详情见 `resources/calculator-guide.md`。脚本接受已核实汇总，不能证明变更语义和集合互斥。

**输出契约。** 交付项目路径说明、每应用边界、基线版本、增删改/不变明细及前后FP、转换明细、完整公式、项目规模、应用新存量或缺口。每项注明可确定/按标准默认值估算/待补充输入/原文歧义待复核（本技能状态约定）。前后功能映射、逐行FP与集合汇总一致才完成；转换与应用存量不得混栏。

## B — 边界

- 项目规模不等于净增量。修改前后均10FP仍可能有10FP增强项目和0FP存量净变动。
- NR02：附录D缺增强前基线、变更属性与完整明细，37FP不能自动解释成增强项目规模。见 `resources/source-issues.md`。
- NR06：项目与应用范围未明确时，不能用子项目分别计数为同一应用共享文件双计背书。
- 不按复用比例或技术工作量折减功能点；不输出工时或报价，除非另有明确换算依据。

相关能力：依赖 `nesma-scope-and-method`、`nesma-elements-and-complexity`；与 `nesma-count-review` 组合审核前后集合。
