# 识别和归组FPA表及其标准事务

## R — 原文与定位

> 对于FPA表ILF，总是计数一个外部输入，一个外部输出和一个外部查询数据表。对于FPA数据表ELF，不需要计数外部输入、输出和查询。

GB/T 42588—2023，6.20，印刷第27页 / PDF第31页。识别条件与归组始于印刷第26页 / PDF第30页；参见7.2.11、8.2.7及相关属性规则7.3.1、8.3.1。

## I — 方法自述

FPA表是按内容和用途识别的特殊实体类别，不是所有名字叫字典、参数或代码表的集合。
先核对其数据是否属于规定的单一数据项、常量、同类解释或独立键的边界/算法等情形。
能由本应用帮助用户维护的FPA表全部归入一个ILF组，外部维护且被引用的全部归入一个ELF组。
维护责任决定分组；系统自带、不能维护的表可能应排除。
各组的不同FPA表数量给RET，相关不同数据元素给DET，再用对应数据功能矩阵。
ILF组的标准事务固定为EI、EO、EQ各一，不能逐表重复附加；ELF组不默认附加这些事务。
标准事务的详细复杂度轴在原文中有疑点，完成确定的分组和数量后必须把这部分留作复核。

## A1 — 原文正反例

类型：原文规范性示例，6.20示例4及示例6，印刷第27页 / PDF第31页，案例c15、c17。

国家实体以国家代码为键，附英文名、法文名等同类解释，符合FPA表的“键＋同类解释”条件。买方实体含买方编号、买方姓名和地区名，地区名属于另一类型数据，原文将其作为非FPA表反例；后者仍需判断是否独立逻辑文件或某文件的一部分。原例未给这两类数据的维护方、全部组成员和具体RET/DET，因此只能完成类型识别，不补出组数或FP。实际应用效果未说明。

## A2 — 触发与邻近区分

- 分类代码/参数数据：“这个字典表算FPA表吗／code table or business entity”。
- 合并代码表：“十张码表是不是十个ILF／group FPA tables by maintenance owner”。
- 复核配套事务：“码表需要几个增删改查”“FPA table standard transactions”。

本卡处理FPA表的识别、归组、数据功能参数与标准事务数量。普通实体关系用 `nesma-logical-data-groups`，普通数据类别用 `nesma-data-functions`，矩阵赋值用 `nesma-elements-and-complexity`。若只是早期模型规模预估，本卡给出归组数量后转 `nesma-indicative-sizing`，不在预估系数之外再加标准事务。

## E — 执行

**输入契约。** 每个候选实体需有ID、字段含义、允许的数据项数量及示例值、是否常量、键及各描述之间关系、用户是否可维护、维护应用、被测应用实际/预期使用的属性。明确当前应用边界和采用预估/估算/详细哪种方式；数量以不同类型计，不以行数或当前实际记录条数计。

1. **判定内容。** 满足以下任一条件可成为FPA表候选，同时检查后述反例：

   | 成立条件 | 需核实的事实 |
   |---|---|
   | 必须且只能含一个数据项 | 是业务约束要求恰好一项，不是当前碰巧只有一条记录；字段数可多 |
   | 原则上只含常量 | 例如化学元素或固定功能点赋值表，不能把可变业务金额称为常量 |
   | 一个键（可复合）＋一个或多个类似解释 | 解释属同类，可有不同语言；多种不同业务数据不能都叫“描述” |
   | 独立关键字＋边界值、算法、最大/最小值 | 键的独立性和参数用途明确，例如范围编号对应最小/最大电话号码 |

   非常量金额、税率、增值税百分比不按FPA表处理；超出上述条件而含多类业务数据的实体也不按FPA表处理。遇未覆盖情形结合用户业务语义核查，不能仅凭名字判定。完成标准：每个候选有成立条件或排除理由。
2. **核实维护和归组。** 所有由本应用帮助用户维护的合为一个FPA表ILF；其他应用维护、被本应用引用的合为一个FPA表ELF。空组不计，一应用最多各一组。不能被维护的实体检查是否系统表；若是系统表则排除；维护方未知则记录待确认。完成标准：每张表归属唯一且维护方有证据。
3. **记录数据功能参数。** 每组 `RET = 不同FPA表总数`；`DET = 组内相关不同数据元素总数`，按7.3.1/8.3.1核查本应用使用/维护或预期使用的属性，未使用属性不盲计；同一类型多条值不增加DET。ILF/ELF的矩阵及权重交复杂度能力。完成标准：RET有表清单、DET有元素清单而非只报数字。
4. **记录标准事务。** FPA表ILF组整体识别 `1 EI + 1 EO + 1 EQ`；FPA表ELF组不因组存在自动加这些事务。其他独立的业务事务仍按自己的证据识别；不得将每张表的增删改各计EI来替代这个特例。完成标准：标准事务具有组ID、类型和“6.20专门规则”标记，并完成去重。
5. **隔离NR04并交接。** 原文对ILF组标准事务要求统计“组内不同实体类型总数，作为引用的记录类型数量”，另统计全部实体中的数据元素总数。保留这两个原文字段，不把前者静默改名FTR，也不因为普通事务排除FPA表FTR就把它设为0。详细计算若依赖该轴映射，输出待核查，暂不自动赋这三项的详细FP。若明确采用估算方式，数据低/事务中的规则由估算汇总能力按已声明方式处理，不称已解释了特殊详细矩阵。完成标准：已确定数据功能、标准事务数量与待核查详细分值分开。

**输出契约。** 逐表表格 `table_id / content_test / evidence / maintenance_owner / used_attributes / group_id / exclusion_reason`；逐组表格 `group_id / ILF_or_ELF / member_tables / RET / DET_items / DET / standard_EI_count / standard_EO_count / standard_EQ_count / original_referenced_record_types / method / unresolved_issue / status`。资源 `measurement-template.json` 可承接；NR04完整说明在 `source-issues.md`。若尚有标准事务未定分值，已确定小计必须明确不是完整规模。

## B — 边界与判停

- 不把普通业务主数据、可变税率或含不同类型数据的实体只凭“字典”名称归入FPA表。
- 未确认维护能力/维护应用时不能把系统表直接变成ILF或ELF。
- NR04仅阻止来源未清的标准事务详细分值自动裁决，不要求丢弃已有依据的组数、RET/DET或标准事务数量。
- 普通事务中的FTR通常排除FPA表组；不要用该排除规则反向抹掉本卡的标准事务。
- FPA表列表、帮助文本、消息字典等特殊交互需按 `nesma-special-functions` 判断，不能再机械多计同一标准查询/输出。
- 预估模型中的两组是公式输入；不能再将本卡标准事务FP叠加到35/15或25/10结果。

## 相关能力

- 对比 `nesma-logical-data-groups`：非FPA实体按关系归组。
- 组合 `nesma-elements-and-complexity`：给已确定的数据组计算复杂度，保留NR04。
- 组合 `nesma-indicative-sizing`：向预估公式提供最多两个FPA计数对象。
- 组合 `nesma-special-functions`：处理来源于FPA表的列表、消息与帮助。
