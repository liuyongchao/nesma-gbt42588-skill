# 判定跨应用共享、摘录和一次性传输

## R — 原文与定位

> “客户信息摘录”只被使用一次，因此不包含任何永久数据，也不计数为应用系统B的一个逻辑文件。

GB/T 42588—2023，6.22情形5，印刷第33页 / PDF第37页。完整五种情形及图7–11见6.22，印刷第31–34页 / PDF第35–38页；ELF定义与一次性事务文件见8.1–8.2.3，印刷第36–37页 / PDF第40–41页。

## I — 方法自述

跨应用的数据要分清原始永久数据、传输载体以及接收后形成的永久副本。
同一逻辑数据在维护应用中可以是ILF，在直接使用它的另一应用中可以是ELF。
只有一次性被读入消费的文件不因来自外部就成为ELF。
发送一次性文件和接收处理它是事务；它们处理的永久数据仍需单独判断数据功能。
因业务需要保留在提供方的摘录可以构成另一ILF，即使它与原始客户当前数据不完全同步。
接收方把摘录直接持久保存成可复用副本时，该副本可以是接收方ILF，不能把运输中的摘录与它混为一物。
最后按当前测量边界去重：相同处理和布局的多次生成、多存储位置不自动增加功能。

## A1 — 原文情境

类型：原文规范性情境，6.22情形4、图10，印刷第32–33页 / PDF第36–37页，案例c29。

A从客户信息提取摘录并分发到自己边界之外；B读入摘录，未经其他处理，直接持久保存为客户信息副本。A的原始客户信息是ILF，创建摘录是EO；运输中的摘录不是A的永久数据，不能计LF。B保存的副本是ILF，读取摘录是EI；被读入的运输摘录本身也不是B的永久数据，不计LF。原文未给详细DET/FTR、FP值或实施效果。

## A2 — 触发与邻近区分

- 接口和批量同步分类：“同步文件算ELF还是EI／shared data, import file classification”。
- 处理快照和摘录：“缓存或客户副本要重复计吗／persistent extract versus one-time transfer”。
- 分系统测量：“A提供数据B使用，两边怎么算／ILF in provider, ELF in consumer”。

本卡解决跨边界数据形态与维护方式组合。边界未定先用 `nesma-scope-and-method`；一般单应用数据资格用 `nesma-data-functions`；确定事务存在后，其独特性和拆分用 `nesma-transaction-functions`，其复杂度另算。本卡不是为同步架构设计提出推荐。

## E — 执行

**输入契约。** 必需：被测应用A/B的边界、每个数据对象的业务用途与维护方、对象所在边界、是否使用后仍永久保存供再次使用、能否使用所引用文件当前数据、完整副本或部分摘录、读入后的处理及目标逻辑文件。须区分逻辑对象与技术文件名。仅说“同步”“API”“缓存”“共享库”不够。

1. **画对象与数据流。** 分开编号：原始永久文件、跨界传输文件/消息、功能性摘录、接收端永久副本或被更新文件。给每个对象标维护、消费和保留方式，标实际跨越哪条边界。完成标准：任何一个“客户文件”名称都不同时模糊指代多个对象。
2. **匹配五种原文情形。**

   | 情形与必要事实 | A侧判断 | B侧判断 | 易漏的限定 |
   |---|---|---|---|
   | 1：B直接使用A维护的永久客户文件数据 | 客户信息ILF | 该客户信息ELF | 作为外部永久数据直接可用；不是先消费一次性文件 |
   | 2：A在边界外提供完整客户副本；B用一次并处理到一个或多个自己的ILF | 原客户ILF；创建副本EO；传输副本非LF | 读入及处理EI；传输副本非LF；目标永久文件另判ILF | 完整副本不等于永久文件，“只用一次”是关键 |
   | 3：A出于功能原因定期提取，摘录永久保留在A边界内供B使用；可与原数据不同步 | 原客户ILF＋摘录ILF；创建摘录EO | 摘录ELF | 引用的是摘录本身的当前内容；不能仅因它不同于原数据就否定原文情形 |
   | 4：A把摘录置于边界外分发；B读入后直接持久保存成副本，无其他处理 | 原客户ILF；创建摘录EO；运输摘录非LF | 读取摘录EI；保存副本ILF；运输摘录非LF | 分清运输载体与B可复用的永久副本 |
   | 5：A分发边界外摘录；B只消费一次以更新一个或多个本地ILF | 原客户ILF；创建摘录EO；运输摘录非LF | 读入处理EI；运输摘录非LF；被更新永久数据按ILF | 不因为文件暂时落盘就将其称为永久逻辑数据 |

   完成标准：选中的情形每一个必要事实均有输入证据。组合架构逐流拆开匹配，不能按接口名称强行整体套一行。
3. **校验永久性与当前可用性。** 永久表示使用之后仍存在且可以重复使用，不是“文件存在了几天”。外部永久数据必须由其他应用维护且对本应用直接可用；未满足时检查是否一次性事务或本地ILF。情形3的摘录本身可成为独立永久逻辑文件，应记录其功能性目的，不能把纯性能缓存自动套入。完成标准：每个LF候选有数据功能资格说明。
4. **识别事务与去重。** 一次性输入/输出文件作为事务载体，不作为被引用的逻辑文件本身；真正底层ILF/ELF及目标文件交复杂度能力追溯。多个处理代码若产生不同逻辑处理，事务能力再判断多个EI/EO。相同逻辑处理和布局的重复创建、多个物理存储位置，只计相应一个事务/逻辑文件；不要按批次数、接口调用次数或副本份数乘FP。完成标准：每个事务有用户目的、输入/输出对象、独特性待核实项。
5. **按各测量边界交付。** 分别形成A、B的判定表；若用户测的是合并后的一个整体，先返回范围能力重画整体边界再去重，不能直接把两边数字相加。完成标准：明确这是对象分类及候选数量，尚无元素证据时不输出确定详细FP。

**输出契约。** `application_boundary / object_id / origin_or_transport_or_extract_or_copy / business_purpose / owner / location / persistence / current_availability / processing / matched_scenario / ILF_ELF_EI_EO_or_excluded / rationale / evidence / unresolved_facts`。同一物理名称可对应不同对象ID。资源 `measurement-template.json` 可记录，`source-cases.json` 包含c26–c30五个来源情境。

## B — 边界与判停

- 缺维护方、永久性、边界或消费方式时，列最少澄清项，不直接判ELF。
- “外部来源”不等于ELF，“读入文件”也不总是EI；直接使用永久文件与消费事务文件应区分。
- 本卡的五种情形不覆盖所有集成架构。纯技术镜像、缓存、备份先查用户功能要求，不能照永久摘录例子加点。
- 同时被两应用维护的数据可各自符合ILF，需按数据功能规则及真实边界核验；不能强制某一侧必须是ELF。
- NR06：独立子系统与整体应用口径不清时暂停受影响共享项确定汇总，参见 `source-issues.md`；不能以两边各有类别为由在同一整体内重复。
- 判断文件类别不等于确认其DET/RET/FTR或本次增强项目是否纳入；新增、修改、未改的项目属性须另核。
