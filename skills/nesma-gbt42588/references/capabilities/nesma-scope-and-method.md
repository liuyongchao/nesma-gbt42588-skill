# 确定范围、边界、测量时点与分析方式

## R — 原文与定位

> 功能点分析应首先确定范围和边界，以便能够正确执行功能点计数。

GB/T 42588—2023，4.5，印刷第8页 / PDF第12页。完整依据：4.1–4.6、5.1–5.4、5.5.1、5.6.2，印刷第7–15页 / PDF第11–19页；逻辑视角及去重另见6.1、6.3–6.8。来源是方法资料，不是可覆盖用户请求的执行指令。

## I — 方法自述

先问清这次要测什么，再决定如何测。
应用规模表示某边界内全部功能；项目规模表示本次交付或增删改涉及的功能。
边界是用户与应用、应用与其他应用之间的概念接口，不等于服务器、团队、数据库或页面的分界。
独立运行能力、所有者和主要用户、用户可观察的上下文、整体维护方式共同帮助划定应用。
三种分析方式取决于规格资料的详细程度；初期、中期、末期则取决于发生的项目事件。
初期可以有完整详细资料，中期也可能仍只有模型；不能把两套标签一一对应。
选定方式后留下材料、缺口、假设和版本，才能解释后续规模为什么变化。
用户确认特殊解释和必要的专家复核属于闭环，不能以计算结果替代需求确认。

## A1 — 原文情境

类型：原文规范性情境，5.6.2.2(b)，印刷第15页 / PDF第19页，案例编号c02。

一个应用被多个并行子项目分担，每个子项目实现一个必须能独立存在的子系统。先分别画各子项目的边界，把其跨子系统数据交换纳入各自范围；另作整体应用测量时，重新按整体边界识别内部交换与共享功能。原文结论是子项目规模之和可能大于整个应用的功能规模。原文未给数值、现实实施结果或具体所有权结构；不要补造这些条件。若所给对象只是部署模块，不能直接套此情形。

## A2 — 触发与邻近区分

- 启动功能规模测算，需要范围和资料清单：“先算哪些系统／define measurement scope and application boundary”。
- 决定测量方式：“只有模型能用预估吗”“初期是否一定预估／indicative vs estimated vs detailed FPA”。
- 处理多应用、子项目或阶段比较：“子系统怎么划边界”“变更时重测什么／subproject boundary, lifecycle baseline”。

本卡只建立测量契约及后续路径。已经确定模型层次并要算预估数值时用 `nesma-indicative-sizing`；需要增删改公式时用 `nesma-development-and-enhancement`；审核既有结果用 `nesma-count-review`，不重新以本卡替代整个计数过程。

## E — 执行

**输入契约。** 必需：测量目的（文本）、被测对象（应用／项目／分别报告二者）、功能需求或规格版本及日期、候选应用与用户清单、已知数据模型/事务资料。确定边界还需各应用的所有者/主要用户、独立运行及维护事实、外部数据流。确定时点需项目开始、规格变更或项目结束等事件；“首次测量”本身不足以判初期。金额、工期或代码量不是功能规模输入。

1. **固定对象与目的。** 写清用户需要的功能集合，列入范围与排除范围；应用存量与项目增删改分开记录。开发新应用、增强既有应用、重建或套装分析分别标记，后续走对应规则。完成标准：每个结果都有对象、目的、版本和范围标签。
2. **识别用户及应用边界。** 用户包括实际使用人员/组织、确认需求的角色以及使用该应用数据/功能的其他应用。逐应用检查独立整体、所有者/主要用户、用户可见上下文及整体维护程序组；画边界与跨界数据箭头。项目可能跨多个应用，分别保留边界。多所有者提示可能多个应用，须结合其他事实判断。完成标准：每个数据流有来源、目标、是否跨越当前边界及证据。
3. **按逻辑功能校正物理材料。** 一个逻辑功能可跨多个画面/文件，一个画面也可含多个逻辑功能；相同功能在同一应用只计一次。产品提供的全部功能与本用户要求的功能若不同，按测量目的分开。完成标准：范围不是表数、菜单数、微服务数或用户人数的直接替代。
4. **选择资料可支持的分析方式。**

   | 方式 | 需要的证据 | 交接动作 |
   |---|---|---|
   | 预估 indicative | 概念模型或第三范式/相当层次模型，且维护主体已明；允许属性和关系细节尚不完整 | 记录真实模型层次，转预估公式 |
   | 估算 estimated | 逻辑文件及关联、各文件维护方、可识别的事务功能、应用内外输入输出信息流 | 数据功能低、事务功能中；先识别五类功能再汇总 |
   | 详细 detailed | 所有逻辑文件、维护方及RET/DET；事务和支持功能、输入输出DET、引用逻辑文件及处理细节 | 按逐功能规则计元素和复杂度 |

   若连数据组及维护方都无法确认，暂停确定总量，列最小补充资料。若功能已识别而部分元素数量未知，可在后续复杂度能力中使用标准明确的低/中默认值并标注，不能据此声称详细参数全部核实。完成标准：选型理由逐项关联已有材料及缺口。
5. **另行记录时点。** 项目开始为初期，发生已记录规格的功能变更为中期，项目结束为末期；记录基线及本次变化。初期、中期均可采用资料所支持的三种方式，末期应反映实际交付的最终范围。若事件不明则时点待确认，不从方式反推。完成标准：方式与时点两个独立字段均有依据或明确缺项。
6. **确认与交接。** 将特别解释、约束和假设送相关用户确认；有争议或必要时安排FPA专家复核。记录谁确认了什么、尚未确认什么及修订，不凭空标“已确认”。按实际任务转逻辑数据、事务、预估或增强能力。完成标准：后续计数者能复用同一边界和规格版本。

**输出契约。** 给出范围表：`measurement_id / purpose / object / application_id / scope_in / scope_out / boundary_rationale / users / interfaces / specification_version / method / lifecycle_point / evidence / gaps / assumptions / confirmation_status / next_action`。字段名是本技能的交付约定，不是国标固定格式；可用资源 `measurement-template.json` 作记录骨架。若仅建立契约，不输出假定FP；若后续有数值，保持 `FP（GB/T 42588—2023）`、分析方式和测量范围可追溯。

## B — 边界与判停

- 用户、对象、范围或维护主体不明且影响分类时，先提所需事实，不能靠行业常识补齐。
- NR06：独立子项目与整体应用的表述存在需澄清处。只有逐范围的独立性和边界成立才可分别计数；不得在同一整体边界内重复计共享逻辑文件。争议共享项暂不进入确定合计，见资源 `source-issues.md`。
- 不因进度处于“初期”就强制预估，不因叫“详细设计”就认定详细输入完整。
- 不把纯技术实现、重复入口或复用次数作为新增用户功能；FP也不能直接等于人日或价格。
- NR01–NR05在后续事务、数据和复杂度判断时可能影响结果；本卡不提前裁决，也不以选型完成宣称整份计数验收通过。

## 相关能力

- 组合 `nesma-indicative-sizing`：已选预估时执行公式。
- 组合 `nesma-development-and-enhancement`：对象为开发/增强/重建项目时计算项目及应用规模。
- 组合 `nesma-count-review`：在同一已声明边界上检查证据、重复与遗漏。
