# 把规范化实体归组为逻辑文件

## R — 原文与定位

> 在双向强制的（1：1）关系中，始终遵循一个逻辑文件对应一个记录类型的规则。

GB/T 42588—2023，6.21.5，印刷第31页 / PDF第35页。完整路径及关系分支见6.21.1–6.21.5、图3–6和表3，印刷第27–31页 / PDF第31–35页；属性去重见7.3.1.3、8.3.1.3。

## I — 方法自述

第三范式实体是数据建模单位，不天然等于用户认可的逻辑文件。
先剥离FPA表和仅表达多对多联系的键—键实体，再判断其他实体的业务独立性。
关系的强制、可选以及一对一、一对多都影响分组，不能只看数据库外键。
单向可选关系要追问删除后另一类数据还有没有独立业务意义，并核对可否重新关联。
依赖实体通常与被依赖实体合成一个逻辑文件，独立实体各成文件。
合并一般保留各实体的记录类型，双向强制一对一是只计一个RET的特例。
归组后的DET来自相关属性，组内引用不能重复计，技术属性不能伪装成用户数据。
模型外可能有功能所需历史数据，模型内也可能有不应计数的临时实体。

## A1 — 原文情境

类型：原文规范性情境，6.21.4图5及6.21.5表3，印刷第29–31页 / PDF第33–35页，案例c24。

A与B为`1:(N)`。若删除A会同时删除所有B，且B脱离A就无业务意义，B依赖A：合成1 LF、2 RET；DET按相关属性合计并排除组内引用重复。若仍有B关联时不准删A，须先处理B或把B连接到其他A，B独立：分别计2 LF。原文以项目和员工补充说明：删除项目通常不要求删除员工，所以员工通常独立。原文未给属性清单与FP结果，不补造复杂度。

## A2 — 触发与邻近区分

- 从ER图建立数据功能：“一张表算一个ILF吗／derive logical files from normalized ER model”。
- 处理主子表和关联表：“订单明细要合并吗”“many-to-many junction entity”。
- 复核RET：“强制一对一算几个RET”“mandatory versus optional relationship”。

本卡确定实体组及RET依据；维护主体决定ILF/ELF类别，交给 `nesma-data-functions`。常量/解码表先走 `nesma-fpa-table-groups`；本卡完成后用 `nesma-elements-and-complexity` 核算属性并赋值。第三范式预估公式的实体数量不应先用本卡全部压缩为LF数。

## E — 执行

**输入契约。** 必需：第三范式或等效模型、实体ID和业务意义、属性用途、关系两端基数及强制/可选性、删除/重关联业务规则、FPA候选标记；确定ILF/ELF还需应用边界和维护方。没有结构化模型时可接受等价文字证据，不能假装已知关系。每个实体、关系及属性均须可定位到规格。

1. **检查候选全集。** 记录模型内所有实体，另查用户需要但模型未列的历史汇总数据。排除纯工作、排序、临时等技术文件；历史文件仍需后续数据功能资格判断。完成标准：模型内外遗漏与排除都有清单。
2. **处理特殊实体。**
   - FPA表按维护方送专门归组，不参与下面的普通实体转换表。
   - 无附加属性的n:m键—键实体不单独赋值；对于它连接的两个逻辑文件，引用属性（外键）按原文计1 DET，按文件保留引用属性的计数记录。
   - 键—键实体仅附带非用户需要的技术日期/时间戳等：忽略这些技术属性，仍按上一种处理。
   - 键—键实体有功能性附加属性：进入普通实体的依赖/独立判断，不能因叫“关联表”就排除。
   完成标准：每个实体只进入一个首要路径，技术字段与功能字段已区分。
3. **核实关系语义。** 括号表示可选；明确哪一端可没有对应记录。`1:(N)`或`1:(1)`考察删A时B怎样处理：随A删除且无独立意义→B依赖；有B就禁止删A、需先独立删除或重关联B→B独立。`(1):N`反向考察删除与A相连的最后一个B：连带删A且A无独立意义→A依赖；A仍关联则不准删最后一个B、须先处理或重关联A→A独立。数据库的级联配置只是线索，不能替代业务意义。完成标准：单向可选关系均有相应删除/重关联证据。
4. **按表3归组。** 下表只适用于排除FPA表及纯键—键实体后的A/B；对称命名可先交换A/B，保持语义一致。

   | A:B关系 | 条件 | 逻辑文件及RET |
   |---|---|---|
   | `(1):(N)` | 双向可选 | 2 LF，各自保留记录类型依据 |
   | `1:N` | 双向强制 | 1 LF、2 RET |
   | `1:(N)` | B依赖A | 1 LF、2 RET |
   | `1:(N)` | B独立A | 2 LF |
   | `(1):N` | A依赖B | 1 LF、2 RET |
   | `(1):N` | A独立B | 2 LF |
   | `(1):(1)` | 双向可选 | 2 LF |
   | `1:1` | 双向强制 | 1 LF、1 RET |
   | `1:(1)` | B依赖A／B独立A | 前者1 LF、2 RET；后者2 LF |

   对两个以上实体形成的同一逻辑文件，一般按组成实体总数确定RET，同时保持双向强制1:1的一个RET特例；复杂关系网络逐组记录推导，不让同一实体重复进入不同普通文件。表3注允许对独立性有疑问时选“实体独立”，必须标记该缺口、采用默认的条文依据与复核事项，而非声称业务证据完整。若连是否FPA表/纯键—键实体或模型层次都不清，不得跳过前置检查直接援引此注。完成标准：每个剩余实体有唯一归组和适用分支。
5. **形成属性和数据功能交接。** 每组列组成实体、RET依据、实际使用/维护的属性；合并内部引用属性不重复计DET。纯键—键联系的引用属性单独留痕，交DET能力核实，不因实体不赋值就一并丢弃联系。由维护责任判定ILF/ELF，再按该类别矩阵计算复杂度。完成标准：归组数、RET与后续DET有可追溯清单，尚未知属性不填0。

**输出契约。** 输出两表：实体处置表 `entity_id / business_meaning / FPA_or_key_key_or_regular / technical_attributes / relation_evidence / disposition`；逻辑文件表 `logical_file_id / entity_ids / relationship_case / independence_evidence / RET / RET_basis / DET_items_pending / maintenance_owner / assumptions / status / source_clause`。本卡可先只交付LF/RET，不要求猜出FP。资源 `measurement-template.json` 可承接记录，`source-cases.json` 保留原文案例。

## B — 边界与判停

- 物理表、外键、建表脚本或级联删除不能单独证明用户的逻辑单元及业务依赖。
- 不把双向强制1:1的1 RET推广到单向可选1:(1)；后者在依赖成立时仍是2 RET。
- 不把所有n:m实体一概排除；存在用户需要的功能属性时必须继续归组判断。
- 模型未列并不等于不计，模型列了并不等于应计；其数据功能资格由后续能力验证。
- 对独立性疑问可用表3注的默认，但记录缺口；未具备模型层次及特殊实体前置条件时停止确定归组。
- 本卡无已确认的独立来源冲突；若后续遇FPA标准事务复杂度NR04或边界NR06，交对应能力及 `source-issues.md` 处理，不用本卡的RET去替代事务FTR。

## 相关能力

- 依赖 `nesma-fpa-table-groups`：普通实体归组前排出FPA表。
- 组合 `nesma-data-functions`：给归组结果判ILF/ELF及纳入资格。
- 组合 `nesma-elements-and-complexity`：根据已确定的组成和属性计算复杂度。
