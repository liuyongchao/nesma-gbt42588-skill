# 识别ILF/ELF与不计数的数据对象

## R — 原文与定位

> 只有当一个逻辑文件不是应用程序的内部逻辑文件时，它才会被计为一个外部逻辑文件，即该应用程序不维护该逻辑文件。

GB/T 42588—2023，8.2.9，印刷第37页 / PDF第41页。完整依据：第7–8章及表5，印刷第34–38页 / PDF第38–42页。

## I — 方法自述

数据功能是用户可认出的永久逻辑数据组，不等于数据库物理对象。
先验证数据的业务用途、实际使用和永久性，再看哪个应用维护它。
本应用使用并维护的为ILF；本应用仅用、由另一应用维护且当前可用的为ELF。
同一逻辑文件在同一应用不同时是ILF和ELF；在不同应用中类别可以不同。
多视图、路径和索引不会增加逻辑文件数，缺少维护说明则要排查而非补造输入事务。
技术临时文件与恢复校验文件应排除；历史数据和纯派生数据要核实独立性及用户需要。
应用存量中的既有文件与增强项目中实际新增或修改的数据功能，是不同范围问题。

## A1 — 原文情境

类型：原文规范性示例，7.2.6、7.2.7、7.2.12，印刷第35页 / PDF第39页，案例c31–c33。

工作、排序、打印等因技术原因引入的文件不计逻辑文件。用户请求重启恢复机制，也不使其校验文件成为可计数数据功能。仅维护派生数据的运行寄存器，若用户明确把它作为需要的数据，可继续按ILF条件判断；仅为性能而加入则不计。原文未给具体属性清单、维护事务或FP，不补出分值。

## A2 — 触发与邻近区分

- 建立数据功能清单：“这组客户/员工数据是ILF还是ELF／classify data function”。
- 排查物理表膨胀：“临时表、历史表、缓存是否计点／technical versus logical data”。
- 维护证据缺失：“有ILF却找不到维护功能／missing maintenance, ILF without EI”。

本卡判数据功能资格及类别。规范化实体先归组用 `nesma-logical-data-groups`；同步/摘录用 `nesma-shared-data`；复杂度用 `nesma-elements-and-complexity`。本卡不负责把尚未识别的功能猜成FP，也不把应用中存在的文件全部算进增强项目。

## E — 执行

**输入契约。** 每个数据组需有逻辑ID、组成实体及用户业务意义、永久性说明、本应用实际使用说明、新增/修改/删除的维护主体与相关功能、当前可用性、是否纯技术用途、需求证据和当前测量边界。物理表名可作线索，不能替代逻辑组。若项目是增强，另需新增/修改/未改/删除状态。

1. **确认逻辑组及资格。** 用用户能理解的对象/数据集合描述，规范化实体按归组能力处理。永久数据在使用后仍可再次使用，一次性消费的传输载体转事务识别。检查模型外用户明确需要的功能数据，排除模型内纯技术对象。完成标准：每组至少有用户识别性、永久性和实际使用证据。
2. **按维护责任分类。**

   | 本应用 | 其他应用 | 本应用计数 | 其他应用计数 |
   |---|---|---|---|
   | 仅使用 | 使用并维护 | ELF（还须当前可直接使用） | ILF |
   | 使用并维护 | 仅使用 | ILF | ELF（还须满足其边界和直接使用条件） |
   | 使用并维护 | 使用并维护 | ILF | ILF |
   | 仅使用 | 仅使用 | 维护方未识别，不能完成分类 | 继续查真实维护方 |

   对同一应用，已判ILF的同一逻辑文件不能再判ELF；ELF须能对应其他应用的ILF。完成标准：分类有“谁使用、谁维护、如何使用当前数据”的证据链。
3. **执行特殊数据检查。**
   - 工作、临时、中间、排序、打印、脱机等纯技术文件不计LF；恢复校验文件也不计，且不作为复杂度引用文件。
   - 视图、访问路径、索引不增加同一逻辑文件数量。
   - 历史文件只有其DET集合相对其他文件独特时才作为独立ILF候选，同时核实用户需要及维护；不要因名叫历史自动单列，也别因模型未画就漏掉。
   - 纯派生数据仅当用户明确要求该数据组且满足其他ILF条件时纳入；纯性能用途排除。
   - 模型外但用户信息需求清楚要求的文件，满足维护/外部提供及当前使用条件仍可计；技术原因所需仍排除。
   - 常量、文本、解码数据走FPA表专门分组。一次性交换文件走共享数据情形，不计ELF。
   完成标准：每项排除或例外均有业务/技术理由，不只依据名称。
4. **排查没有维护功能的候选ILF。** 第一支：其他应用维护，检查应为ELF还是一次性输入事务文件；第二支：用户需求漏写了本应用真实维护过程，询问并在取得证据后补记；第三支：实为技术解决方案文件，排除。不能仅因完整性规则而虚构EI。ELF可以只被读取用于EI的验证/编辑，因此没有单独EO/EQ时不一定错误。完成标准：未闭合项记录问题、待确认角色和下一步证据。
5. **在边界及对象上去重。** 同一整体应用的多子系统共享LF只计一次，按整体是否维护判ILF或ELF；跨真正独立应用分别判。NR06涉及独立子项目和应用口径时先澄清。增强项目不纳入既有且没有任何改变的ILF/ELF；它们仍可能留在应用存量或被事务引用。完成标准：数据功能存在性、应用类别和本项目是否纳入分别有字段。
6. **交接复杂度与审查。** 保留组成实体、实际用/维护的属性、相关维护/引用事务。按 `nesma-elements-and-complexity` 核RET/DET并赋值；用 `nesma-count-review` 检查引用关系和证据。完成标准：未确定的属性或事务不被当成0，未闭合组不冒充最终清单。

**输出契约。** `logical_file_id / entities / user_meaning / permanent / used_by / maintained_by / directly_current / category / included_in_application / project_change_status / included_in_project / related_transactions / exclusion_reason / evidence / assumptions / review_issue / status`。字段为交付约定，资源 `measurement-template.json` 可承接；输出已确定、待确认和排除三类清单，必要时给部分数量，不给无依据完整FP。

## B — 边界与判停

- 维护主体未知、应用边界不清或永久性缺证据时，停在候选状态；不得凭读写权限、库所在服务器或命名推定责任。
- NR05：6.19/10.2.6要求ILF有EO，7.2.4写EO或EQ。缺EO但有EQ时列复核问题；不能自动补EO，也不能无条件宣布完整性通过。
- NR06：独立子项目分开计的情形不支持在同一个整体应用里重复计共享文件；口径不明时不汇总受影响项。
- NR04的FPA标准事务复杂度不由本卡裁决；数据组类别已确定不代表其所有附属事务已定分值。
- NR01/NR02附录D案例不能代替本项目的数据维护、变更状态或完整DET清单；NR03系统消息属于事务元素问题。六组问题均见资源 `source-issues.md`。

## 相关能力

- 依赖 `nesma-logical-data-groups`：从规范化实体得到用户逻辑组。
- 组合 `nesma-shared-data`：处理跨应用永久数据、摘录与传输载体。
- 组合 `nesma-elements-and-complexity`：在分类完成后计算数据复杂度。
- 组合 `nesma-count-review`：核查维护缺口、重复及项目纳入依据。
